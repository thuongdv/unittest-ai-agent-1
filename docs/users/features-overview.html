Unit Test AI Agents: what this project delivers

Six AI coding agents that analyze a repository, turn Jira requirements into test scenarios, write unit tests, review them against the requirements, repair failing tests, and write a report for developers and QA, plus an orchestrator that runs each workflow from a single command. They use the repository's own test tools and run in Claude Code, OpenAI Codex CLI, Gemini CLI, and GitHub Copilot. The agents are plain Markdown instructions: there are no scripts and no install step beyond copying files.

One-time setup, then one command per workflow

You set up a repository once with the analyzer. After that, the orchestrator runs each workflow from a single command. It calls the agents in order, reads each JSON result to choose the next step, and keeps every step under one run-id.

Setup: run once per repository

Workflow 1: generate, review, and fix new tests

Workflow 2: diagnose and repair failing tests

WorkflowOne commandThe same steps run by hand
Setup/codebase-analyzer(not orchestrated)
1. Generate & review/unit-test-orchestrator <targets> [--jira <keys>][/unit-test-requirement-analyzer --jira <keys> →] /unit-test-generator <targets> [--requirements <run-id>] → /unit-test-reviewer <run-id> → /unit-test-generator --fix <run-id> → /unit-test-reporter <run-id>
2. Diagnose & repair/unit-test-orchestrator --failures …/unit-test-failure-analyzer … → /unit-test-generator --repair-failures <run-id> → /unit-test-reporter <run-id>

Requirements & report: tests that check the business rule, not the code

If tests are written only from the code, a wrong implementation produces tests that pass and lock in the wrong behavior. Example: the ticket says a 10% discount starts at $100, the code starts it above $200, and every code-derived test still passes. With requirements, expected results come from the ticket, and the reviewer compares ticket, tests, and code.

Result per requirementMeaningWho acts
passEvery scenario has a passing test with the requirement's expected valueNo one
bugThe test matches the requirement, but the code does not; the test is kept and skipped as a defectDeveloper
test issueA scenario has no test, or a test asserts the code's value instead of the requirement'sGenerator (--fix)
unclearThe requirement does not say what should happenBA / PO
not coveredNo code in the given targets implements itQA

report.md opens with one recommendation (for example "Do not merge. Fix production code"), then a scorecard, the defects to fix with file and line, a requirement → scenario → test traceability table for QA, and the questions for the BA. It is plain Markdown, so CI can post it to a pull request.

The agents

Every agent and the orchestrator read .unit-test-agent/project.json, which the analyzer writes during setup. They all stop at once if that file is missing, has an unsupported version, or still has a blocking open question. You can still run each agent on its own.

F01

Codebase Analyzer

/codebase-analyzer [subproject]
  • Detects language, package manager, test framework, mocking library, and coverage and mutation tools
  • Finds the install, typecheck, lint, test, coverage, and mutation commands
  • Runs the existing tests once to record a baseline
  • Records a confidence level and the evidence for each detected value
  • Lists open questions as blocking or non-blocking
  • Keeps your manual edits when you run it again
Writes project.json
F02

Generator: Generate mode

/unit-test-generator <targets>
  • Writes happy-path, edge, boundary, and error test cases
  • With --requirements, takes every expected value from the requirement scenarios, not from the code
  • Copies the style of your existing test files
  • Fixes its own broken tests, up to a set number of attempts
  • Keeps adding tests until the coverage thresholds are met
  • Explains every line it could not cover
Writes runs/<id>/generation.json
F03

Generator: Fix mode

/unit-test-generator --fix <run-id>
  • Changes only the tests the reviewer flagged
  • Replaces weak assertions with stronger ones
  • Adds tests that catch surviving mutants and cover missed branches
  • Never deletes an assertion to clear a finding
Writes runs/<id>/generation.r<N>.json
F04

Test Reviewer

/unit-test-reviewer <run-id>
  • Runs in a fresh subagent, so it starts without the generator's reasoning
  • Checks every test case against a 9-point rubric
  • Rates each requirement as pass, bug, test issue, unclear, or not covered
  • Runs mutation testing on the target files when a mutation tool is configured
  • Runs the new tests 3 times to catch flaky ones
  • Never edits code
Writes runs/<id>/review.json
F05

Failure Analyzer

/unit-test-failure-analyzer [targets | --log file]
  • Runs the failing tests, or reads an existing log
  • Reads the test, the source code, and recent git history
  • Puts each failure in one of 6 root-cause categories, with evidence
  • When it cannot tell, assumes a source bug so a valid test is never rewritten
  • Never edits code
Writes runs/<id>/failure-analysis.json
F06

Generator: Repair-Failures mode

/unit-test-generator --repair-failures <run-id>
  • Fixes outdated tests, broken mocks, flaky tests, and import errors
  • Keeps the assertions of tests that caught a real bug, and marks those tests as skipped
  • Records environment problems without changing any file
  • Runs the tests again to confirm the suite passes
Writes runs/<id>/failure-repair.json
F12

Orchestrator

/unit-test-orchestrator <targets> | --failures …
  • Runs a whole workflow from one command
  • Chooses the next step from each agent's JSON result
  • Caps the review and fix loop (--max-review-rounds, default 3)
  • Stops at the first failed step and says which one failed
  • Never runs the analyzer, and has no rules of its own for writing or judging tests
Writes nothing itself; ends every workflow with the reporter
F13

Requirement Analyzer

/unit-test-requirement-analyzer --jira KEY
  • Reads Jira issues through the Jira MCP server (or exported files with --req-file)
  • Runs in an isolated subagent and never reads source or test code
  • Extracts business rules and boundary scenarios with expected results
  • Turns ambiguities into questions instead of guessing
  • Never writes to Jira
Writes runs/<id>/requirements.json
F14

Reporter

/unit-test-reporter <run-id>
  • One recommendation with an owner: developer, QA, or BA
  • Defects to fix, with file, line, and the test to re-enable
  • Requirement traceability and open questions for QA and BA
  • Only renders the run's JSON; adds no findings of its own
Writes runs/<id>/report.md

Inside Generate mode

Guardrails

Every agent follows these rules. The automated checks (F11) verify them after each evaluation run.

  • Production code is never modified. Agents write only under the configured test folders and .unit-test-agent/.
  • Failing tests are never "fixed" by weakening them. An agent never deletes or loosens an assertion, and never changes an expected value to match buggy output.
  • Bugs found in your code are reported. The agent keeps the correct assertion, marks the test as skipped or expected-to-fail using the framework's own mechanism, and records the bug in suspectedDefects with the expected and actual behavior.
  • Expected results come from the requirement, not the code. When requirements are given, tests assert what the ticket says; the requirement analyzer never reads code and never writes to Jira.
  • Agents check before they act. If configuration is missing, a schema version is unsupported, or a blocking question is unanswered, the agent stops and tells you what to do.
  • Every output can be traced. Each JSON file records its schema version, the agent that wrote it, a timestamp, and a run ID.

Failure triage: how a red test gets resolved

CategoryMeaningActionOutcome
stale_testThe source contract changed on purpose, and the change is documented. The test is out of date.Update the testfixed
broken_mock_or_fixtureA mock or fixture no longer matches the real interface.Fix the mock or setupfixed
flaky_or_nondeterministicTiming, randomness, the clock, or test order changes the result.Stabilize the testfixed
syntax_or_import_errorA broken import or a compile error.Update the test (if the error is in the test file)fixed
source_regression_bugThe test is right and the production code is wrong.Skip the test and report the defectskipped_defect
environment_or_dependencyA missing dependency, environment variable, or service.Fix the environment (you do this)blocked_env

A stale_test classified with low confidence is handled as a source bug, so a real regression is never hidden.

Review rubric

The reviewer checks every test case against nine criteria and rates each finding critical, major, or minor. It requests changes if any finding is critical or major, if any test is flaky, or if a mutant survives that a test could have caught.

#CriterionWhat it catches
1missing_branch_or_edge_caseBranches, error paths, or boundary values that no test checks
2duplicate_caseTwo tests that cover the same code path with the same kind of input
3implementation_detail_couplingTests that assert private state or call counts instead of observable results
4over_mockingMocks of pure helpers or value objects that did not need mocking
5non_determinismReal clocks, unseeded randomness, real network or file I/O, or state shared between tests
6weak_or_tautological_assertionAssertions like toBeDefined() or assert True, or checking that a mock returns what it was set up to return
7naming_and_style_mismatchTests that do not follow the conventions of your existing test files
8missing_requirement_scenarioA requirement scenario that no test checks
9expected_value_mirrors_implementationA test that asserts what the code returns instead of what the requirement says

Installation: copy two folders

Each agent's instructions are stored in one place. Each runtime gets a 5–15 line wrapper that points to those instructions, so changing a rule means editing one file.

mkdir -p <repo>/.unit-test-agent
cp -r agents schemas <repo>/.unit-test-agent/
cp -r runtimes/claude/.claude <repo>/          # or codex / gemini / copilot

<repo>/.unit-test-agent/
├── agents/            # instructions (commit)
├── schemas/           # JSON contracts (commit)
├── project.json       # written by the analyzer; edit freely (commit)
└── runs/<run-id>/     # per-run reports (optionally gitignored)
    ├── requirements.json · generation.json · generation.r1.json · review.json
    ├── failure-analysis.json · failure-repair.json
    └── report.md      # the human-readable result

You can tune project.json, for example the coverage thresholds (up to 100%) and maxRepairAttempts. Running the analyzer again keeps your edits.

How the project tests its own agents

F07

JSON contracts

  • 6 JSON Schema (Draft 2020-12) files, one per output type
  • Strict: an unknown field fails validation, so a typo in a field name is caught
  • Every detected value records a confidence level and its evidence
F09

Example fixtures

  • examples/ts-vitest and examples/py-pytest
  • Each one contains a deliberate bug, an unreachable guard, and seeded failing tests (one stale test and one real regression)
  • Each one has a requirement file and a module whose code and docs agree but break that requirement
  • Includes a sample CI log and a manual test procedure
F11

Automated output checks

  • A Vitest package for contributors that inspects the outputs and git state after a run
  • Runs the same 15 checks for every runtime
  • Reports the pass rate across repeated runs
F08 · F10

Packaging & user guide

  • Thin wrappers for all 6 agents and the orchestrator in all 4 runtimes
  • A README with installation commands for each runtime, both workflows, and how to customize the agents
